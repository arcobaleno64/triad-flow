## 1. 執行摘要與里程碑願景 (Executive Summary & Vision)

Triad-Flow 在 **v2.11.0** 成功奠定了以 `ContainerDriver` 為核心的 Patch Jail 容器隔離架構與跨 7 大語言生態系（Python、Rust、Go、C、C++、JS、TS）的修復對齊。然而，在實務高併發審查與多弱點批次修復情境下，每次調度皆啟動冷容器（Cold Container Spawn）造成顯著啟動延遲（每次執行約 1.5 ~ 3 秒），且單機循序執行無法有效滿足千行級單元、跨檔案與 Monorepo 的審查吞吐量。

**Triad-Flow v2.12 里程碑** 將引領系統邁向高吞吐、低延遲與實體動態反例驗證的三大革新：
1. **容器沙盒熱重載池 (Hot-Reuse Container Pool)**：透過長駐暖機容器池與單元級工作區熱掛載，將指令調度額外開銷降至 P95 < 150ms，並輔以嚴格跨任務隔離與淘汰機制。
2. **分散式異質審查協調器 (Distributed Swarm Orchestrator)**：支援大跨度變更集的依賴感知分塊與多 Agent 節點並行派發，搭配 Ed25519/HMAC 防偽防重放數位憑據鏈。
3. **主動式 PoC 反例合成器 (Active PoC Test Synthesizer)**：在 Patch Jail 容器內為待審弱點動態生成重現腳本，以具備因果鏈的特定弱點特徵驗證取代單純退出碼比對。

全架構嚴格維持 **零外部執行時期 npm 依賴 (`"dependencies": {}`)** 與 Node.js 18+ 跨平台規範。

## 2. 核心架構支柱與防禦性規格 (Core Architectural Pillars)

### 支柱 1：容器沙盒熱重載與工作區池化架構 (Hot-Reuse Container Pool)
- **架構設計**：
  - 實作 `ContainerSandboxPool`，依語言映像檔（Node、Python、Rust、Go、C/C++）預先啟動長駐暖機容器（Warm Daemons）。
  - 同步支援 Docker (`docker exec -i`) 與 rootless Podman (`podman exec -i`) 多工轉發指令，避免反覆建構/拆卸容器所導致的 I/O 與程序負擔。
  - **啟動期主動外聯探針 (Startup Egress Probe)**：暖機容器啟動入池前，強制執行對外網路探針，證實容器網路處於完全封閉狀態（Egress Denied），始可列入就緒佇列。
- **跨任務隔離與容器淘汰條件 (Cross-Task Isolation & Retirement)**：
  - **任務輪換上限 (Task Count Ceiling)**：容器設定最大執行次數（預設 $N=10$），達標後強制銷毀重建，防止隱蔽背景程序（Zombie Processes）、未釋放記憶體、跨任務快取或殘留機密跨環境污染。
  - **工作區物理清洗 (Workspace Scrubbing)**：每輪任務執行完畢後，掛載目錄必須即刻執行硬性清理，容器內部工作區目錄必須回到基線狀態。
  - **嚴格資源限制**：容器設定硬性記憶體上限（`--memory 2g`）、CPU 限額（`--cpus 2.0`）與非特權降權機制（`--user 1000:1000`）。
- **外部獨立 Reconciler 與殘留容器回收 (External Garbage Collection Reconciler)**：
  - 不做「單靠行程訊號處理器即保證零孤兒容器」的不實假設；針對主機無預警斷電、當機或遭 `SIGKILL (kill -9)` 終止等訊號無法捕捉之邊界情況，建立獨立 Reconciler 機制。
  - 容器啟動時統一注入識別標籤 `triad-flow-sandbox=pool`、`triad-flow-run-id=<id>` 與啟動時間戳；Reconciler 定期或於每次 CLI 啟動前掃描清理超過生存時間（TTL，預設 1 小時）的孤兒容器。
- **延遲指標定義與權衡基準 (Latency SLA Specification)**：
  - 定義 `150ms` 為**容器熱命令轉發（Command Dispatch Overhead）之 P95 目標**（P99 < 300ms）。
  - 測量範圍嚴格限制於指令轉發與 IPC 回傳開銷，不包含測試指令本身運行耗時；嚴禁為了追求效能數字而妥協目錄清洗與隔離驗證完整性。

### 支柱 2：分散式異質審查協調器 (Distributed Swarm Orchestrator)
- **依賴感知分塊派發 (Dependency-Aware Partitioning)**：
  - 基於 AST 跨檔案符號關聯（Call-Graph & Symbol References）對 PR 變更進行模組聚類，防止割裂相互依賴的函式邊界。
  - 支援多 Worker 並行處理獨立子模組，並將審查結果匯流至中央共識引擎。
- **真實性防偽與防重放憑據鏈 (Authenticity & Anti-Replay Evidence Chain)**：
  - 拒絕單純以「SHA-256 + 時間戳」作為來源證明；各分散式節點回傳報告必須經由 **Ed25519 非對稱數位簽署或節點 HMAC 驗證**。
  - 憑據必須強制綁定中央分發的單次隨機數（Per-Run Nonce）、Exact-Head Commit SHA 與 ChangeSet ContentDigest，防範中間人偽造與重放攻擊。
  - 中央協調器在合成總結報告前，逐一核對信任錨點清冊（Trust Anchors），確保節點身份真實性。
- **抗震盪降級通道 (Fail-Closed Circuit Breaker)**：
  - 若特定 Worker 逾時或中斷，協調器自動觸發重試或將該子集標記為 `UNINSPECTED_CHUNK`，絕不靜默吞沒或發放未經檢驗的合格權威。

### 支柱 3：主動式 PoC 反例合成器 (Active PoC Test Synthesizer)
- **弱點專屬的可驗證行為因果鏈 (Observable Vulnerability Mechanics)**：
  - 解決當前審查引擎主要依賴現有測試套件的限制；針對新增程式碼或缺乏測試的弱點路徑，由 Verifier 在 Patch Jail 容器中合成最小可重現測試（PoC Harness）。
  - **PoC 本身視為不可信代碼 (Untrusted PoC Containment)**：合成的測試腳本本身必須置於 Patch Jail 嚴格沙盒內運行，施加硬性逾時限額（預設 $T \le 15\text{s}$）以防範死迴圈（如 CWE-835）或惡意利用腳本造成的次級逃逸。
  - **拒絕粗糙退出碼判定**：嚴禁以「Pre-Patch 非零退出碼」作為成功重現之單一依據，徹底排除缺少依賴、語法錯誤或路徑不存在造成的非零假陽性。
  - **特定弱點特徵驗證 (Given-When-Then)**：PoC 驗收必須提供明確因果鏈——如 CWE-22 必須證實越權讀取目標檔案內容；CWE-89 必須證實查詢邏輯遭竄改；CWE-416 必須觸發明確之記憶體存取異常信號或 ASan 崩潰資訊。
- **修復前後雙向對照 (Differential Verification)**：
  - 修復前（Pre-Patch）：PoC 執行必須明確觸發前述預期的安全違規特徵。
  - 修復後（Post-Patch）：PoC 執行必須完全通過（Exit 0 且行為符合預期），且專案既有迴歸測試套件不得亮紅燈。
- **資產沉澱 (Asset Hardening)**：
  - 驗證通過之 PoC 自動轉換為專案標準迴歸測試，杜絕未來同類型弱點復發。

### 支柱 4：弱點分類感知的動態異質仲裁 (Taxonomy-Aware Quorum Calibration)
- **實證數據驅動之特化校準 (Empirical Benchmark Calibration)**：
  - 拒絕未經證實的主觀模型領域假說；模型權重必須基於 TF-OSS-v2 / TF-OSS-v3 真實世界基準測試的實測數據（召回率、精確率與誤報率）進行動態校準。
  - 初步驗證假設（待基準數據確認）：
    - 底層記憶體安全（CWE-119, CWE-416, CWE-190）：重點檢驗 Codex 語意定位。
    - 業務邏輯、並行競爭與狀態機（CWE-362, CWE-835, CWE-755）：重點檢驗 Claude 語意推理。
    - 全域架構掃描與 Monorepo 關聯：運用 Antigravity (AGY) 廣域上下文捕捉。
- **動態加權與 Fail-Closed 閘門底線**：
  - 動態計分僅用於提升審查訊噪比與排序，任何權重計算均不得突破 **Fail-Closed 裁定底線**。
  - 一旦出現跨模型實質分歧（Disagreement Ledger），嚴格保留人機迴圈（Human-in-the-loop）的人工裁決權限。
